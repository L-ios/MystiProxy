# F5 入站 IP 过滤（允许/拒绝列表）— Proposal

## 需求深度理解

### 背景与问题

`docs/DEVELOPMENT.md` 的 4 层转发待实现清单明确列有：**"根据请求的 IP 过滤请求，或者拒绝连接"**。当前实现中没有任何入站过滤——`http/server.rs` 与 `proxy/mod.rs` 的 accept 循环对每个连接无条件服务。

### 深层需求分析

这是运维安全边界需求，典型场景：

- 代理端口只允许内网网段（10.0.0.0/8）访问，公网扫描直接拒绝
- Docker socket 转发（unix→tcp）场景下，仅允许本机/特定容器网段使用
- 拒绝已知恶意来源

设计要点权衡：
1. **CIDR 而非单 IP**：真实运维按网段授权；需支持 IPv4 与 IPv6 CIDR
2. **allow 优先还是 deny 优先**：业界通行（nginx allow/deny）是顺序无关的 `allow` 列表 + 隐式拒绝剩余，或 `deny` 列表 + 隐式允许剩余。本项目配置已有 header/locations 等字段，采用显式 `allow`+`deny` 双列表、**deny 先判（黑名单优先拒绝）、无配置则全放行**的语义，最不易意外锁死服务
3. **作用层级**：在 accept 后立即判定（对 TCP 与 HTTP 引擎统一生效），拒绝时直接 close，不进入任何解析逻辑——这是纵深防御的正确位置

### 用户价值

- 代理引擎获得网络层访问控制，满足"内网专用代理"部署形态
- 填补 DEVELOPMENT.md 4 层转发的最后一个可做缺口（UDP 已明确文档化为不支持）

### 成功标准

1. 配置 `allow: ["10.0.0.0/8"]` 时，非 10.x 客户端连接被关闭（curl 观察到连接重置），10.x 正常服务
2. `deny: ["192.168.1.5/32"]` 精确拒绝该 IP，其他放行
3. deny 与 allow 同时配置时 deny 优先
4. 无任何配置 → 行为与现状完全一致（零回归）
5. 非法 CIDR 启动报配置错误
6. 覆盖率 ≥70%，workspace 全绿，Actions 全绿

### 范围

做：`IpFilter` 模块（CIDR 解析+匹配）、`EngineConfig` 新字段 `allow`/`deny`（Option<Vec<String>>）、TCP 与 HTTP 两个 accept 循环接入、单元+集成测试、文档勾选。
不做：地理 IP、动态黑名单 API、按 location 差异化过滤（后续可在 7 层细化）。

## 信心评估

- CIDR 匹配：标准位运算，且检查发现 `http/proxy.rs` 已有 `allow_host/block_host`（域名级，正向代理用），语义参考一致，**信心 93%**
- IPv6 前缀比较：128 位分组比较，标准实现，**信心 90%**
- accept 层接入：两个循环各加 3 行，**信心 95%**
- 全部 >85%，无需网络调研。
